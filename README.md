## 1. Description
<div align="right"><a href="#toc">[목차로]</a></div>

두 개의 스택(a, b)과 11가지 명령어만으로 정수 목록을 오름차순으로 정렬하되,
**가능한 한 적은 수의 명령어**로 정렬하는 순서를 찾아 출력하는 프로그램입니다.

프로그램은 정렬된 숫자를 출력하지 않습니다. 대신 `sa`, `pb`, `ra` 같은 명령어 목록을 출력하고,
그 명령어들을 순서대로 실행하면 스택 a가 정렬되고 스택 b가 비게 됩니다.
채점은 출력된 명령어의 줄 수로 이루어집니다.

원소 수에 따라 전용 정렬을 쓰고, 6개 이상은 **청크 분할과 탐욕적 삽입**을 결합한 방식으로 정렬합니다.

<a id="sec-1-1"></a>
### 1.1 결과
<div align="right"><a href="#toc">[목차로]</a></div>

무작위 입력을 반복 실행해 측정한 연산 수(출력된 명령어 줄 수)입니다. (Ubuntu, `checker_linux`로 정렬 여부 검증)

| 원소 수 | 기준 (100%) | 시도 횟수 | 최소 | 평균 | 최대 | 정렬 실패 |
|---|---|---|---|---|---|---|
| 100개 | 700 미만 | 1,000 | 497 | 555.7 | **631** | 0 |
| 500개 | 5,500 이하 | 1,000 | 3,591 | 약 3,947 | **4,294** | 0 |

두 기준 모두 **최악의 경우에도** 통과합니다.\
int 전체 범위의 음수·양수에 `INT_MIN`과 `INT_MAX`를 매번 포함한 입력으로도, 100개와 500개 모두 정렬 실패 0회를 확인했습니다.

#### 1.2.1.1 전처리: 좌표 압축
<div align="right"><a href="#toc">[목차로]</a></div>

정렬을 시작하기 전에, 모든 값을 **0부터 n-1까지의 순위**로 바꿉니다.
대소 관계는 그대로 보존되므로, 이후 모든 판단은 순위로 합니다.

**순위로 바꾸는 방법**

`a = [42, -7, 100]`을 예로 들면 다음 네 단계를 거칩니다.

| 단계 | 하는 일 | 결과 |
|---|---|---|
| 1. 복사 | a의 값들을 비어 있는 b의 저장 공간에 복사 | `[42, -7, 100]` |
| 2. 힙 정렬 | 복사본을 오름차순으로 정렬 | `[-7, 42, 100]` |
| 3. 이진 탐색 | a의 값마다 정렬된 복사본에서 몇 번째 칸에 있는지 찾음 | 42 → 1, -7 → 0, 100 → 2 |
| 4. 덮어쓰기 | a의 값을 찾은 칸 번호로 바꿈 | `a = [1, 0, 2]` |

**정렬된 배열에서의 칸 번호가 곧 순위**입니다. 가장 작은 값은 0번 칸, 그다음 값은 1번 칸에 놓이기 때문입니다.
중복이 없으므로 칸 번호가 겹치지 않습니다.

**이 방법을 고른 이유**

- **b의 공간을 빌리는 이유**: 이 시점에 b는 비어 있으므로, `malloc`을 더 하지 않고 임시 공간으로 씁니다.
- **힙 정렬인 이유**: 추가 공간 없이 제자리에서 정렬하며, 최악의 경우에도 O(n log n)입니다. 병합 정렬은 임시 배열이 따로 필요합니다.
- **이진 탐색인 이유**: 정렬된 배열에서 값 하나를 찾는 데 O(log n)이므로, 전체가 O(n log n)입니다.
  "나보다 작은 값이 몇 개인가"를 값마다 일일이 세면 O(n²)이 됩니다.

#### 1.2.1.2 원소 수에 따른 분기
<div align="right"><a href="#toc">[목차로]</a></div>

| 원소 수 | 방식 | 최대 연산 수 |
|---|---|---|
| 이미 정렬됨 | 아무것도 출력하지 않음 | 0 |
| 2개 | 뒤집혀 있으면 `sa` | 1 |
| 3개 | 최댓값을 맨 아래로 보낸 뒤(`ra` 또는 `rra`), 위 두 개가 뒤집혀 있으면 `sa` | 2 |
| 4~5개 | 최솟값을 하나씩 b로 보내 a를 3개로 줄이고, 3개 정렬 후 전부 되돌림 | 10 |
| 6개 이상 | 청크 알고리즘 (1.2.1.3) | — |

<a id="sec-1-2-1-3"></a>
#### 1.2.1.3 청크 알고리즘
<div align="right"><a href="#toc">[목차로]</a></div>

##### 1.2.1.3.1 1단계: a → b
<div align="right"><a href="#toc">[목차로]</a></div>

순위를 몇 개의 구간(청크)으로 묶고, **작은 순위 구간에 속하는 원소부터** b로 보냅니다.
구간은 스택의 자리가 아니라 **값의 범위**이므로, 같은 구간의 원소는 a 여기저기에 흩어져 있습니다.

- a의 맨 위가 지금 구간에 속하면 `pb`, 아니면 `ra`로 넘깁니다.
- 구간의 아래쪽 절반 값은 b에 넣은 뒤 `rb`로 b의 맨 아래로 내립니다.
  구간 하나가 b 안에서 위아래 두 덩어리로 나뉘어, a를 다시 훑지 않고도 더 잘게 정리됩니다.
- 이때 a의 다음 원소가 구간 밖이라 `ra`도 필요하면, `rb`와 `ra`를 `rr` 하나로 합칩니다.
- a에 3개가 남으면 멈추고, 그 3개를 정렬합니다.

##### 1.2.1.3.2 2단계: b → a
<div align="right"><a href="#toc">[목차로]</a></div>

b의 원소를 하나씩 a의 제자리에 끼워 넣습니다.

`pa`는 원소를 a의 **맨 위에만** 올릴 수 있으므로, 제자리에 넣으려면
`pa` 직전에 **정렬 순서상 바로 다음 값**이 a의 맨 위에 있어야 합니다.

| 경우 | a의 맨 위로 올릴 값 |
|---|---|
| 넣을 값보다 큰 값이 a에 있음 | 그중 가장 작은 값 |
| 넣을 값보다 큰 값이 없음 | a의 최솟값 (a가 원형이라 맨 끝 다음이 맨 처음) |

b의 **모든 원소**에 대해 다음 네 조합의 회전 수를 계산하고, 가장 싼 원소를 골라 실행한 뒤 `pa`합니다.
(A = a에서 목표 값의 위치, B = b에서 지금 비용을 계산하고 있는 원소의 위치)

| 조합 | 회전 수 | 비고 |
|---|---|---|
| `ra` + `rb` | pick_greater(A, B) | 겹치는 만큼 `rr`로 합침 |
| `rra` + `rrb` | pick_greater(a크기 − A, b크기 − B) | 겹치는 만큼 `rrr`로 합침 |
| `ra` + `rrb` | A + (b크기 − B) | 방향이 달라 합칠 수 없음 |
| `rra` + `rb` | (a크기 − A) + B | 방향이 달라 합칠 수 없음 |

`pick_greater`는 두 값 중 큰 쪽을 돌려줍니다. (`cost.c`)
같은 방향으로 돌릴 때는 겹치는 만큼 한 번에 처리하고 남은 쪽만 따로 돌리므로,
결국 큰 쪽의 횟수만큼만 들게 됩니다.

원소를 하나 넣을 때마다 두 스택이 모두 바뀌므로, 비용은 **매번 처음부터 다시** 계산합니다.

##### 1.2.1.3.3 3단계: 마무리 회전
<div align="right"><a href="#toc">[목차로]</a></div>

2단계가 끝난 a는 정렬되어 있지만 회전된 상태일 수 있습니다.
최솟값을 더 짧은 방향(`ra` 또는 `rra`)으로 맨 위까지 돌립니다.

<a id="sec-1-2-1-4"></a>
#### 1.2.1.4 핵심 철학: 매 단계 최선을 고르면 전체도 충분히 좋다
<div align="right"><a href="#toc">[목차로]</a></div>

2단계의 설계는 모두 이 전제 위에 서 있습니다.

원소 하나를 넣는 비용(회전 수 + `pa` 1번)은 **정확하게** 계산됩니다.
매 단계에서 가장 싼 원소를 고르는 것도 **그 단계에서는** 정확한 최선입니다.

하지만 이것이 **전체 연산 수의 최소를 보장하지는 않습니다.**
지금 싼 원소를 먼저 넣은 결과, 나중에 넣을 원소들이 비싸질 수도 있기 때문입니다.
전체 최적을 구하려면 넣는 순서의 모든 경우를 따져봐야 하는데,
원소가 500개면 그 경우의 수가 천문학적이라 현실적으로 불가능합니다.

그래서 이 프로젝트는 **"매 단계 최선을 고르면 전체도 충분히 좋다"** 는 전제를 받아들였고,
그 전제가 충분히 맞는지는 벤치마크로 확인했습니다. (1.1 결과 참고)

<a id="sec-1-2-1-5"></a>
#### 1.2.1.5 탐욕적으로 개선된 삽입정렬
<div align="right"><a href="#toc">[목차로]</a></div>

두 단계를 기존 정렬 알고리즘에 비유하면 이렇습니다.

- **1단계**는 선택정렬과 달리 매번 정확한 최솟값을 찾지 않습니다.(선택정렬(selection sort)은 남은 원소 중에서 가장 작은 것을 "선택"해서 맨 앞으로 보내는 과정을 반복하는 정렬입니다.)
  지금 구간에 속하기만 하면 순서를 따지지 않고 옮깁니다.
- **2단계**는 삽입정렬과 비슷합니다. 이미 정리된 a의 올바른 자리에 원소를 하나씩 끼워 넣으니까요.
  다만 일반 삽입정렬처럼 **정해진 순서대로** 다음 원소를 넣는 대신,
  **매번 비용이 가장 싼 원소부터** 고른다는 점에서 "탐욕적으로 개선된 삽입정렬"에 가깝습니다.

일반 삽입정렬에는 다음 원소를 고를 자유가 없지만,
push_swap에서는 b의 원소 중 무엇을 먼저 되돌릴지 **선택할 자유**가 있습니다.
그 자유가 곧 최적화의 여지입니다.

<a id="sec-1-2-1-6"></a>
#### 1.2.1.6 청크 개수는 실측으로 정했습니다
<div align="right"><a href="#toc">[목차로]</a></div>

청크는 스택의 구간이 아니라 **원소 순위값의 범위**입니다.

청크 개수에는 서로 반대로 움직이는 두 비용이 걸려 있습니다.

| 청크 개수가 적으면 | 청크 개수가 많으면 |
|---|---|
| a를 훑는 횟수가 적어 1단계가 쌈 | a를 여러 번 훑어야 해서 1단계가 비쌈 |
| b가 거칠게 정리되어 2단계가 비쌈 | b가 촘촘히 정리되어 2단계가 쌈 |

흔히 알려진 값(100개에 5, 500개에 11)은 구현마다 최적이 달라 출발점으로만 삼고,
청크 개수를 바꿔가며 각각 무작위 입력 100회씩 실행해 **최대 연산 수**를 비교했습니다.

| 100개 | 청크 1 | **청크 2** | 청크 3 | 청크 4 | 청크 5 | 청크 6 |
|---|---|---|---|---|---|---|
| 최대 | 637 | **612** | 646 | 667 | 700 | 723 |

| 500개 | 청크 2 | **청크 3** | 청크 5 | 청크 8 | 청크 11 |
|---|---|---|---|---|---|
| 최대 | 4,298 | **4,261** | 4,435 | 4,893 | 5,471 |

그 결과 **100개 이하는 청크 2개, 100개 초과는 청크 3개**로 정했습니다. (`push_chunks.c`의 `choose_chunk_size`)

흔히 알려진 값보다 훨씬 적은 개수가 최적으로 나온 것은,
1단계에서 구간의 아래쪽 절반을 b의 맨 아래로 내리는 처리가
청크를 한 번 더 나누는 효과를 내기 때문으로 보입니다.

> <details>
> <summary>"1단계에서 구간의 아래쪽 절반을 b의 맨 아래로 내리는 처리"란...</summary>
>
> <br>
>
> `push_chunks.c`에서 원소를 `pb`한 직후, 그 원소가 지금 청크의 아래쪽 절반(작은 순위 쪽)이면 `rb`를 한 번 더 하는 부분입니다.
>
> - 청크의 위쪽 절반(큰 순위): `pb`만 → b의 맨 위에 쌓임
> - 청크의 아래쪽 절반(작은 순위): `pb` 후 `rb` → b의 맨 아래로 내려감
>
> **아주 작은 예**
>
> 청크 하나가 순위 0 ~ 3을 맡고, 기준은 2라고 하겠습니다. (0, 1은 아래쪽 절반, 2, 3은 위쪽 절반)
>
> ```
> a: 3 0 2 1   (왼쪽이 맨 위)
> ```
>
> | 원소 | 절반 | 연산 | b (왼쪽이 맨 위) |
> |---|---|---|---|
> | 3 | 위 | `pb` | 3 |
> | 0 | 아래 | `pb`, `rb` | 3 0 |
> | 2 | 위 | `pb` | 2 3 0 |
> | 1 | 아래 | `pb`, `rb` | 2 3 0 1 |
>
> 결과는 이렇습니다.
>
> ```
> b: 2 3 | 0 1   (| 왼쪽이 위쪽 절반, 오른쪽이 아래쪽 절반)
> ```
>
> `rb` 없이 `pb`만 했다면 b는 `1 2 0 3`처럼 두 절반이 뒤섞였을 겁니다.
>
> </details>

<a id="sec-1-2-2-1"></a>
#### 1.2.2.1 원형 버퍼 (circular buffer)
<div align="right"><a href="#toc">[목차로]</a></div>

- **핵심 아이디어**: 배열의 끝과 처음을 이어 원처럼 쓰고, 원소를 옮기는 대신 **시작 위치(`head`)만 옮깁니다.**
- **쓰인 곳**: 스택 a와 b의 저장 구조입니다.
  회전(`ra`, `rra` 등)과 `push`를 원소 이동 없이 `head` 계산만으로 처리합니다. (`access.c`, `ops_*.c`)
  → 1.2.3.2

<a id="sec-1-2-2-2"></a>
#### 1.2.2.2 좌표 압축 (coordinate compression)
<div align="right"><a href="#toc">[목차로]</a></div>

- **핵심 아이디어**: 값을 크기 순위로 바꿔도 대소 관계는 그대로이므로,
  임의의 정수를 **0부터 n-1까지의 순위**로 바꿔 다룹니다.
- **쓰인 곳**: 정렬 전처리입니다. 청크를 순위 범위로 나누고,
  "구간 상한 미만의 값은 정확히 그 상한만큼 있다"는 성질로 구간을 다 보냈는지 판정합니다. (`ranks.c`)

<a id="sec-1-2-2-3"></a>
#### 1.2.2.3 힙 정렬 (heap sort): 느슨한 규칙으로 쌓은 무더기(heap)에서 최댓값을 하나씩 꺼내는 정렬
<div align="right"><a href="#toc">[목차로]</a></div>

- **핵심 아이디어**: 여기서 "느슨한 규칙"은 "부모가 자식보다 크다"는 것 하나뿐이라는 뜻입니다. 배열을 인덱스 규칙(`i`번 칸의 자식은 `2i+1`, `2i+2`번 칸)만으로 이진 트리로 읽어,
  최댓값이 맨 위에 오는 힙을 만든 뒤 하나씩 꺼내 뒤쪽부터 채웁니다.
  **추가 공간 없이, 최악의 경우에도 O(n log n)** 입니다.
- **쓰인 곳**: 좌표 압축에서 값의 복사본을 정렬합니다.
  복사본을 비어 있는 b의 저장 공간에 두기 때문에, 임시 배열이 필요한 병합 정렬 대신
  제자리에서 정렬하는 힙 정렬을 골랐습니다. (`ranks.c`)

<a id="sec-1-2-2-4"></a>
#### 1.2.2.4 이진 탐색 (binary search)
<div align="right"><a href="#toc">[목차로]</a></div>

- **핵심 아이디어**: 정렬된 상태를 이용해 가운데 값과 비교하며 **탐색 범위를 절반씩 좁힙니다.** O(log n)입니다.
- **쓰인 곳**: 좌표 압축에서 정렬된 복사본 안의 각 값의 위치를 찾습니다.
  중복이 없으므로 **찾은 위치가 곧 순위**입니다. (`ranks.c`)

<a id="sec-1-2-2-5"></a>
#### 1.2.2.5 청크 분할: 값의 범위로 나눠 담는 분배 방식
<div align="right"><a href="#toc">[목차로]</a></div>

- **핵심 아이디어**: 값의 범위를 몇 개의 구간으로 나누고, **원소 자신의 값만 보고** 목적지를 정합니다.
  다른 원소와 비교하지 않으므로, 스택의 맨 위만 보고도 판단할 수 있습니다.
  이런 방식을 통틀어 분배 정렬이라고 부릅니다. 값의 범위로 나눠 담는다는 점에서 버킷 정렬의 분배 단계와 같은 발상이며,
  자릿수마다 반복해 나누는 기수 정렬과는 다릅니다.
- **쓰인 곳**: 알고리즘의 1단계(a → b)입니다. (`push_chunks.c`) → 1.2.1.3.1

<summary><a id="sec-1-2-3"></a><b>1.2.3 기술적 선택: 왜 그렇게 했나</b> &nbsp; <a href="#toc">[목차로]</a></summary>

<a id="sec-1-2-3-1"></a>
#### 1.2.3.1 스택 자료구조: 배열 vs 연결 리스트
<div align="right"><a href="#toc">[목차로]</a></div>

스택 a와 b를 연결 리스트가 아닌 **배열**로 구현했습니다.

| | 배열 | 연결 리스트 |
|---|---|---|
| 위에서 n번째 원소 접근 | 즉시 (O(1)) | 앞에서부터 따라가야 함 (O(n)) |
| 비용 계산의 중첩 반복문 | 위치 번호가 곧 인덱스라 단순함 | 포인터와 위치 카운터를 함께 관리해야 함 |
| 메모리 할당과 해제 | a, b 각 1번씩, 총 2번 | 원소마다 1번, 해제도 순회하며 하나씩 |
| 실수하기 쉬운 곳 | 인덱스 범위 | 포인터 끊김, 누수 |

**선택의 근거는 두 가지입니다.**

첫째, 2단계의 비용 계산은 "b의 모든 원소에 대해, a에서 목표 값이 몇 번째에 있는가"를 반복해서 묻습니다.
배열에서는 위치 번호가 곧 인덱스라 이 반복이 단순해집니다.

둘째, `malloc`이 두 번뿐이라 에러 경로에서 해제할 것이 적습니다.
실제로 valgrind 확인 결과, 할당이 일어나는 모든 경로에서 **2 allocs, 2 frees**로 끝납니다.
(파싱 에러와 인자 없음은 할당 전에 종료하므로 0 allocs입니다.)

**배열의 대가도 있습니다.** 평범한 배열은 회전할 때마다 원소를 통째로 밀어야 하고,
인덱스를 잘못 계산하면 배열 밖의 메모리를 건드립니다.
앞의 문제는 원형 버퍼로 해결했고(1.2.3.2), 뒤의 문제는 인덱스 계산을
한 파일(`access.c`)에 모아 실수할 자리를 줄였습니다.

**연결 리스트로도 100% 기준 달성은 가능합니다.**
따라서 이것은 가능과 불가능의 문제가 아니라, 코드의 번거로움과 실수 위험의 차이입니다.

또한 채점 기준은 **출력된 명령어의 줄 수**이지 프로그램 내부의 계산량이 아닙니다.
배열에서 원소를 몇 번 옮기든, 연결 리스트에서 몇 번 순회하든 출력되는 명령어 수는 같습니다.

그래서 결론은 "배열이 우월하다"가 아니라,
**"이 프로젝트의 채점 기준과 제약에서는 배열 쪽의 대가가 더 싸다"** 입니다.

<a id="sec-1-2-3-2"></a>
#### 1.2.3.2 원형 버퍼
<div align="right"><a href="#toc">[목차로]</a></div>

##### 1.2.3.2.1 왜 원형 버퍼인가
<div align="right"><a href="#toc">[목차로]</a></div>

평범한 배열로 스택을 만들면, 회전할 때마다 원소를 통째로 밀어야 합니다.
500개짜리 스택이라면 `ra` 한 번에 **원소 500번 이동**이 필요하고, 정렬 도중 회전은 수천 번 일어납니다.

원형 버퍼에서는 원소를 옮기지 않고 스택의 맨 위를 가리키는 `head`만 옮깁니다.
회전은 원소 수가 변하지 않으므로, `head`에 대한 **덧셈 한 번과 AND 연산 한 번**으로 끝납니다.
`push`도 마찬가지로 `head`를 한 칸 옮기고 값 하나를 쓰는 것으로 처리됩니다.

이 최적화는 채점 기준(출력 줄 수)과 무관합니다.
채점 기준을 지키면서도 **같은 전력 대비 효율적으로 동작하는 프로그램**을 만들고자 도입했습니다.

##### 1.2.3.2.2 두 가지 번호 체계: `position`과 `idx`
<div align="right"><a href="#toc">[목차로]</a></div>

원형 버퍼에는 번호 체계가 두 가지 있습니다. 코드를 읽을 때 이 둘을 구분하는 것이 가장 중요합니다.

| 이름 | 뜻 |
|---|---|
| `position` | 스택의 위에서 몇 번째인가 (0이 맨 위). 스택을 다루는 모든 코드가 쓰는 번호 |
| `idx` | `data` 배열의 몇 번 칸인가. `access.c` 안에서만 쓰는 번호 |

둘은 이렇게 연결되며, **`head`가 0일 때만 같습니다.**

```
idx = (head + position) & (capacity - 1)
```

`capacity` 8, `head` 3, 원소 5개인 예입니다.

```
data:      [ ? ][ ? ][ ? ][ 4 ][ 2 ][ 0 ][ 3 ][ 1 ]
idx:         0    1    2    3    4    5    6    7
                            ↑ head
position:                   0    1    2    3    4
```

최솟값 0의 `position`은 **2**이고, 실제로 놓인 `idx`는 **5**입니다.
`find_min_position`이 `idx`가 아니라 `position`을 돌려주는 이유는,
**그 값이 곧 맨 위로 끌어올리는 데 필요한 `ra`의 횟수**이기 때문입니다.

이 번역은 `access.c`의 `stack_get`, `stack_set` 안에서만 일어납니다.
나머지 코드는 전부 `position`만 다루므로, 원형 버퍼 계산을 빠뜨릴 수 없는 구조입니다.

##### 1.2.3.2.3 `capacity`를 2의 거듭제곱으로 잡은 이유
<div align="right"><a href="#toc">[목차로]</a></div>

`capacity`는 원소 수 이상인 가장 작은 2의 거듭제곱으로 잡습니다. (500개 → 512)
그러면 나머지 연산 `% capacity`를 비트 AND `& (capacity - 1)`로 바꿀 수 있습니다.

10진수에서 100으로 나눈 나머지는 뒤 두 자리만 보면 되듯이,
2진수에서 512(= 2⁹)로 나눈 나머지는 **하위 9비트만 남기면** 됩니다.
`& 511`이 정확히 그 일을 합니다.

| 연산 | 소요 |
|---|---|
| 나눗셈 (`%`) | 약 20~40 사이클 |
| 비트 AND (`&`) | 약 1 사이클 |

이 계산은 원소에 접근할 때마다 일어나므로 차이가 쌓입니다.

`head`는 0 ~ `capacity-1`, `position`은 0 ~ `size-1`(≤ `capacity-1`)이므로,
`head + position`은 최대 `2 × capacity - 2`입니다.
**두 바퀴를 넘는 일이 없어**, 한 번 잘라내는 것만으로 정확하게 순환합니다.

##### 1.2.3.2.4 음수와 2의 보수
<div align="right"><a href="#toc">[목차로]</a></div>

`rra`나 `push`처럼 `head`를 배열의 이전 칸으로 옮길 때, `head`가 0이면 `head - 1`은 -1이 됩니다.

```c
head = (head - 1) & (capacity - 1);
```

-1은 2의 보수 표현에서 **모든 비트가 1**이므로, 하위 비트만 남기면 `capacity - 1`,
즉 배열의 마지막 칸이 됩니다. 0번 칸의 이전 칸이 마지막 칸이니 원형으로서 정확한 결과입니다.

이것이 가능한 이유는 **2의 보수 표현 자체가 2의 거듭제곱에 대한 나머지 연산 구조**이기 때문입니다.
32비트 정수는 2³²에 대한 나머지로 값을 담고, 원형 버퍼는 2ᵏ에 대한 나머지로 칸을 셉니다.
2ᵏ가 2³²을 나누어떨어지게 하므로, 큰 원에서의 위치가 작은 원에 그대로 옮겨집니다.

반면 C의 정수 나눗셈은 몫의 소수점 아래를 잘라내므로(-0.125 → 0), 나머지가 나뉘는 수의 부호를 따릅니다. 그래서 `-1 % 8`은 7이 아니라 **-1**이 되어 배열 밖을 가리킵니다.

| 식 | `head`가 0일 때 결과 |
|---|---|
| `(head - 1) & (capacity - 1)` | 마지막 칸 ✓ |
| `(head - 1) % capacity` | -1 ✗ |

그래서 `capacity`를 한 번 더해 양수로 만드는 처리(`+ capacity`)를 따로 두지 않고,
2의 보수가 만들어내는 올바른 순환 결과를 그대로 활용했습니다.
**단, 이 방식은 `&` 전용이며 `%`로 바꾸면 깨집니다.**
(C23부터는 2의 보수가 표준으로 정해졌고, 실제로 쓰이는 모든 기계가 2의 보수를 씁니다.)

##### 1.2.3.2.5 원소 수가 `capacity`보다 적을 때의 회전
<div align="right"><a href="#toc">[목차로]</a></div>

원소가 5개이고 `capacity`가 8이면, 스택의 맨 아래 다음 칸은 **빈 칸**입니다.
이때 `head`만 옮기면 그 빈 칸이 스택 안으로 들어와 버립니다.

그래서 회전할 때 값 하나를 복사합니다.

| 연산 | 처리 |
|---|---|
| `ra` | 맨 위 값을 `position` = `size` 자리(맨 아래의 다음 칸)에 복사한 뒤, `head`를 다음 칸으로 |
| `rra` | `head`를 이전 칸으로 옮긴 뒤, 옛 맨 아래 값(새 기준 `position` = `size`)을 새 맨 위에 복사 |

원소 수가 `capacity`와 같을 때는 복사하는 자리가 원래 같은 값이 있던 칸이라 아무 영향이 없습니다.
**나머지 원소들은 여전히 움직이지 않으므로**, 원소 500번 이동이 1번 복사로 줄어든 이득은 그대로입니다.

이 문제는 원소 수와 `capacity`가 같은 입력(`1 2 3 4`)만으로 테스트했을 때는 드러나지 않았고,
**원소 수가 `capacity`보다 적은 입력**(`5 1 2 3 4` 등)으로 테스트하면서 발견해 고쳤습니다.

##### 1.2.3.2.6 대가
<div align="right"><a href="#toc">[목차로]</a></div>

- 모든 원소 접근에 인덱스 계산이 붙습니다.
- 인덱스 계산을 잘못하면 조용히 엉뚱한 원소를 읽거나 배열 밖을 건드리며, 원인 찾기가 어렵습니다.

이를 줄이기 위해 세 가지를 했습니다.

- 인덱스 계산을 `access.c`의 두 함수(`stack_get`, `stack_set`)에만 두었습니다.
- `position`과 `idx`로 이름을 나눠, 어느 번호인지 변수 이름만 보고 알 수 있게 했습니다.
- AddressSanitizer로 원소 수가 `capacity`와 같은 경우와 다른 경우를 모두 확인했습니다.

<a id="sec-1-2-3-3"></a>
#### 1.2.3.3 파싱
<div align="right"><a href="#toc">[목차로]</a></div>

##### 1.2.3.3.1 한 인자 안의 여러 숫자
<div align="right"><a href="#toc">[목차로]</a></div>

숫자를 인자별로 따로 넣어도, 한 인자 안에 공백으로 이어 넣어도 받습니다.

```bash
./push_swap 3 1 2        # 인자 셋
./push_swap "3 1 2"      # 인자 하나
./push_swap "3 1" 2      # 섞어서
```

**이유는 셸 차이입니다.** subject 13쪽의 평가 예시는 이렇습니다.

```bash
ARG="4 67 3 87 23"; ./push_swap $ARG
```

bash와 sh는 따옴표 없는 `$ARG`를 공백으로 쪼개 다섯 개의 인자로 넘기지만,
**zsh은 기본적으로 쪼개지 않아** `"4 67 3 87 23"`이 인자 하나로 들어옵니다.
42 클러스터의 기본 셸은 zsh이고 평가자는 이 예시를 그대로 입력하므로,
한 인자 안의 공백도 프로그램이 직접 나누도록 했습니다.
그래서 어느 셸에서든 평가 예시가 그대로 동작합니다.

| 입력 | 결과 |
|---|---|
| `"3  1"` (공백 여러 개), `" 3 1 "` (앞뒤 공백) | 정상 |
| `""` (빈 인자) | Error |
| `" "` (공백만 있는 인자) | Error |
| `"3 1" "" 2` (중간에 빈 인자) | Error |

숫자가 하나도 없는 인자는 Error로 처리합니다.
subject 17쪽의 예시(`./checker "" 1` → `Error`)와 같은 기준입니다.
구분자는 스페이스만 인정합니다.

**문자열을 새로 할당하지 않고 제자리에서 읽습니다.**
`ft_split`처럼 잘라낸 조각을 새로 할당하는 대신, 원래 인자 문자열 위에서
공백을 건너뛰고 숫자 하나를 읽고 다시 공백을 건너뛰는 식으로 포인터만 옮겨갑니다. (`args.c`)
그래서 `malloc`은 여전히 a, b 두 번뿐이고, libft도 쓰지 않았습니다.

허용하는 숫자 형식은 부호 하나(`+` 또는 `-`)와 숫자뿐입니다. `+5`, `-3`, `007`은 정상 입력입니다.

##### 1.2.3.3.2 오버플로 검사
<div align="right"><a href="#toc">[목차로]</a></div>

`ft_atoi`나 표준 `atoi`는 int 범위를 넘는 값을 감지하지 못하므로, 변환 함수를 직접 작성했습니다.

**더 넓은 타입에 누적한 뒤 범위를 검사합니다.**
`int`로 받으면 오버플로가 일어난 뒤에는 원래 값을 알 수 없고,
부호 있는 정수의 오버플로는 C 표준에서 미정의 동작이라 검사 코드 자체를 신뢰할 수 없습니다.

**`long`이 아니라 `long long`을 썼습니다.**
C 표준은 `long`을 최소 32비트로만 보장하며, 실제로 64비트 Windows에서 `long`은 32비트입니다.
`long long`은 최소 64비트가 보장되어 어느 플랫폼에서도 int 범위를 넉넉히 담습니다.

**매 자릿수마다 검사합니다.**
반복문이 끝난 뒤 한 번만 검사하면, 자릿수가 아주 많은 입력에서 `long long`마저 넘칠 수 있습니다.

> <details>
> <summary>"<code>long long</code>마저 넘칠 수 있습니다"란...</summary>
>
> <br>
>
> `long long`도 담을 수 있는 크기에 한계가 있다는 뜻입니다.
>
> ```
> LLONG_MAX = 9223372036854775807   (19자리)
> ```
>
> 숫자를 읽을 때는 한 자리씩 `result = result * 10 + 자릿수`로 쌓습니다. 입력이 20자리를 넘으면, 쌓는 **도중에** `long long`의 한계를 넘어버립니다.
>
> **끝에서 한 번만 검사하면**
>
> ```c
> while (숫자가 남아 있는 동안)
> {
> 	result = result * 10 + 자릿수;     /* 20자리째에서 이미 넘침 */
> }
> if (result > 2147483647)               /* 이미 망가진 값을 검사 */
> ```
>
> 부호 있는 정수가 넘치는 순간부터는 미정의 동작이라 값을 믿을 수 없습니다. 실제로는 보통 한 바퀴 돌아 엉뚱한 값이 되는데, 예를 들어 `18446744073709551617`(2⁶⁴ + 1)을 넣으면 쌓인 값이 돌고 돌아 **1**이 될 수 있습니다. 그러면 끝의 검사는 "1이니 범위 안"이라고 통과시켜, 터무니없이 큰 수를 **1로 받아들이는** 버그가 됩니다.
>
> **매 자릿수마다 검사하면**
>
> ```c
> while (숫자가 남아 있는 동안)
> {
> 	result = result * 10 + 자릿수;
> 	if (result > 2147483648)           /* 넘는 즉시 Error */
> 	{
> 		exit_error();
> 	}
> }
> ```
>
> `result`가 2147483648을 넘는 순간 바로 멈추니, 가장 커봐야 그 직전 값에 10을 곱하고 9를 더한 **약 214억**입니다. `long long`의 한계(약 922경)에는 한참 못 미치므로, 입력이 몇 자리든 넘칠 일이 없습니다.
>
> </details>

**int 범위의 비대칭을 반영했습니다.**

```
INT_MIN = -2147483648
INT_MAX =  2147483647
```

음수 쪽이 하나 더 크므로, 절댓값을 누적하며 2147483648까지는 허용하고
양수일 때만 2147483647을 넘는지 한 번 더 검사합니다.

##### 1.2.3.3.3 검증을 메모리 할당보다 먼저
<div align="right"><a href="#toc">[목차로]</a></div>

```
1. 모든 인자의 모든 숫자를 검증하며 개수를 셈   ← 실패해도 해제할 것이 없음 (count_numbers)
2. 센 개수만큼 스택 a, b 할당
3. 같은 길을 다시 걸으며 값을 채움              ← 이미 검증됐으므로 실패하지 않음 (fill_stack)
4. 중복 검사                                    ← 실패하면 해제 후 종료
```

한 인자에 숫자가 몇 개 있는지 모르므로, 몇 칸을 할당할지 정하려면 할당 전에 한 번 세야 합니다.
그때 검증까지 끝내두면, 파싱 에러는 **해제할 메모리가 없는 시점**에 일어납니다.
그래서 에러 종료 함수를 인자 없이 단순하게 유지할 수 있습니다.

대가는 "각 숫자를 두 번 변환한다"는 것입니다.

> <details>
> <summary>"각 숫자를 두 번 변환한다"란...</summary>
>
> <br>
>
> 같은 숫자 문자열에 `parse_int`를 두 번 부른다는 뜻입니다.
>
> | 차례 | 어디서 | 목적 |
> |---|---|---|
> | 1번째 | `count_numbers` (할당 **전**) | 형식과 범위가 맞는지 **검증**하고 개수를 세기. 변환된 값은 버림 |
> | 2번째 | `fill_stack` (할당 **후**) | 같은 문자열을 다시 변환해 그 값을 스택 a에 **저장** |
>
> 첫 번째 변환 결과를 저장해 두려면 할당이 먼저 필요한데, 그러면 "검증을 할당보다 먼저"라는 순서가 깨집니다. 그래서 한 번 더 변환하는 쪽을 택한 것입니다.
>
> </details>

하지만 이는 프로그램 내부의 계산량일 뿐 채점 기준(출력 줄 수)과 무관하고,
500개 기준으로도 전체 실행 시간에서 무시할 만한 비중입니다.

중복 검사만은 값이 배열에 들어간 뒤에야 할 수 있으므로,
이 경우에는 할당한 메모리를 해제한 뒤 종료합니다. (`exit_error_free`)

모든 에러 메시지는 **표준 에러**로 출력되어, 명령어 목록과 섞이지 않습니다.

<a id="sec-1-2-3-4"></a>
#### 1.2.3.4 출력 버퍼링
<div align="right"><a href="#toc">[목차로]</a></div>

##### 1.2.3.4.1 왜 모아서 내보내는가
<div align="right"><a href="#toc">[목차로]</a></div>

명령어를 하나 만들 때마다 `write`를 부르면, 500개 정렬에서 약 5,500번의 **시스템 콜**이 일어납니다.
시스템 콜은 사용자 모드에서 커널 모드로 전환하는 작업이라, 일반 함수 호출보다 훨씬 비쌉니다.

그래서 명령어를 메모리의 버퍼에 쌓아두었다가, 마지막에 한 번에 내보냅니다.

```
5,500번의 write  →  1번의 write
```

이 역시 채점 기준과는 무관하며, 같은 전력 대비 효율을 위한 선택입니다.

##### 1.2.3.4.2 버퍼 크기: 32,768바이트
<div align="right"><a href="#toc">[목차로]</a></div>

500개 정렬 시 명령어 약 5,500개 × 한 줄 최대 4바이트(`rrr\n`) = 약 22KB입니다.
여유를 두어 32KB로 잡았고, 이 크기면 `write`가 한 번만 호출됩니다.

**이 값이 실제 필요량보다 작아도 동작에는 문제가 없습니다.**
버퍼가 넘칠 것 같으면 먼저 비우고 이어서 쓰기 때문입니다.
예를 들어 1,000개를 정렬하면 `write`가 두 번 불릴 뿐, 출력 내용은 같습니다.

즉 버퍼 크기는 **"얼마나 빠른가"만 결정하고, "맞는가"는 결정하지 않습니다.**
최적화가 정확성을 위협하지 않도록 설계했습니다.

##### 1.2.3.4.3 전역 변수 없이 버퍼를 전달하는 방법
<div align="right"><a href="#toc">[목차로]</a></div>

subject는 전역 변수를 금지합니다. 그래서 두 스택과 버퍼를 하나의 구조체로 묶어 함수 사이로 넘깁니다.

```c
typedef struct s_machine
{
	t_stack	a;
	t_stack	b;
	char	bff[BUFFER_SIZE];
	int		bff_len;
}	t_machine;
```

push_swap을 **두 스택과 명령어 출력 포트를 가진 하나의 기계**로 보고 `t_machine`이라 이름 붙였습니다.

파일 범위의 `static` 변수로 버퍼를 둘 수도 있지만 쓰지 않았습니다.
명령어를 출력하는 연산 함수들은 스택을 조작하기 위해 어차피 `t_machine`을 받으므로 얻는 이득이 없고,
파일 범위의 `static` 변수는 그 파일의 함수들이 함께 쓰는 상태라는 점에서 전역 변수와 성질이 같아, subject의 금지 조항에 걸릴 여지가 있기 때문입니다. (`static` 함수는 이름을 파일 안으로 숨길 뿐 상태를 갖지 않으므로 이와 무관하며, 이 프로젝트에서도 여러 곳에 씁니다.)

버퍼는 `malloc` 없이 구조체 안의 배열로 두었습니다. 크기가 고정이라 동적 할당이 필요 없고, 해제할 것도 없습니다.

##### 1.2.3.4.4 에러가 나면 아무것도 출력하지 않음
<div align="right"><a href="#toc">[목차로]</a></div>

모든 에러는 명령어가 하나도 쌓이기 전인 파싱 단계에서 일어납니다.
에러 경로에서는 버퍼를 비우지 않고 종료하므로, 명령어가 섞여 나가는 일이 없습니다.

<a id="sec-1-2-3-5"></a>
#### 1.2.3.5 효과 없는 연산도 그대로 출력함
<div align="right"><a href="#toc">[목차로]</a></div>

원소가 하나뿐인 스택에 `sa`를 하는 것처럼, 연산이 실제로는 아무 효과가 없는 경우가 있습니다.
subject도 이런 경우 "아무것도 하지 않는다"고 정해두었습니다.

이때도 **명령어는 그대로 출력**합니다.

- checker도 똑같이 아무것도 하지 않으므로, 두 쪽의 스택 상태가 어긋나지 않습니다.
- 출력을 건너뛰면 연산 수는 줄지만, 알고리즘이 **불필요한 연산을 부르고 있다는 사실이 가려집니다.**
  정상적인 알고리즘이라면 애초에 그런 상황에서 연산을 부르지 않아야 합니다.

그래서 효과 없는 연산은 출력 단계에서 감추지 않고, **부르는 쪽에서 막았습니다.**
예를 들어 1단계에서 b에 원소가 하나뿐일 때는 `rb`를 부르지 않습니다. (`push_chunks.c`)

<a id="sec-1-2-3-6"></a>
#### 1.2.3.6 결합 연산은 한 줄로 출력함
<div align="right"><a href="#toc">[목차로]</a></div>

`ss`, `rr`, `rrr`은 두 스택을 동시에 조작하지만 **명령어 한 줄**입니다.
이를 구현할 때 `op_sa`와 `op_sb`를 차례로 부르면 `sa`, `sb` 두 줄이 출력되어 결합 연산의 이점이 사라집니다.

그래서 결합 연산은 출력하지 않는 내부 함수(`swap_stack`, `rotate_stack` 등)를 두 번 부른 뒤,
명령어를 한 번만 출력합니다.

</details>

## 2. Instructions
<div align="right"><a href="#toc">[목차로]</a></div>

<a id="sec-2-1"></a>
### 2.1 빌드
<div align="right"><a href="#toc">[목차로]</a></div>

```bash
make          # push_swap 빌드
make clean    # 오브젝트 파일 삭제
make fclean   # 오브젝트 파일과 실행 파일 삭제
make re       # 전부 지우고 다시 빌드
```

컴파일러는 `cc`, 플래그는 `-Wall -Wextra -Werror`입니다. 외부 라이브러리(libft 포함)는 쓰지 않습니다.

메모리 오류를 확인하기 위한 별도 빌드도 있습니다.

```bash
make asan     # AddressSanitizer 가 들어간 push_swap_asan 빌드
make re_asan  # 전부 지우고 push_swap_asan 다시 빌드
```

<a id="sec-2-2"></a>
### 2.2 실행
<div align="right"><a href="#toc">[목차로]</a></div>

```bash
./push_swap 3 2 1
```

```
ra
sa
```

첫 번째 인자가 스택 a의 맨 위입니다.

숫자는 인자별로 나눠 넣어도, 한 인자 안에 공백으로 이어 넣어도 됩니다. (1.2.3.3.1 참고)
그래서 아래 명령들은 bash와 zsh 어느 셸에서든 그대로 동작합니다.

연산 수를 세려면:

```bash
ARG="4 67 3 87 23"; ./push_swap $ARG | wc -l
```

정렬이 맞는지 확인하려면 42가 제공하는 checker를 씁니다.

```bash
ARG="4 67 3 87 23"; ./push_swap $ARG | ./checker_linux $ARG
```

`OK`가 나오면 정렬된 것입니다.

무작위 입력으로 확인하려면 (Linux):

```bash
ARG=$(shuf -i 1-100 | tr '\n' ' '); ./push_swap $ARG | ./checker_linux $ARG
ARG=$(shuf -i 1-100 | tr '\n' ' '); ./push_swap $ARG | wc -l
```

<a id="sec-2-3"></a>
### 2.3 입력 규칙
<div align="right"><a href="#toc">[목차로]</a></div>

| 입력 | 동작 |
|---|---|
| 인자 없음 | 아무것도 출력하지 않음 |
| 이미 정렬됨 | 아무것도 출력하지 않음 |
| 한 인자에 여러 수 (`"3 1 2"`, `"3 1" 2`) | 정상 입력 (1.2.3.3.1 참고) |
| 공백 여러 개, 앞뒤 공백 (`"3  1"`, `" 3 1 "`) | 정상 입력 |
| 부호와 앞자리 0 (`+5`, `-3`, `007`) | 정상 입력 |
| 숫자가 아닌 것 (`abc`, `1-2`, `-`, `"- 3"`) | `Error` |
| 숫자가 없는 인자 (`""`, `" "`) | `Error` |
| int 범위를 벗어난 값 (`2147483648`) | `Error` |
| 중복된 값 (`"3 1 3"`, `"3 1" 3`) | `Error` |

`Error`는 표준 에러로 출력되므로, 명령어 목록과 섞이지 않습니다.

```bash
./push_swap 1 2 abc 2>/dev/null    # 아무것도 보이지 않음
```

<a id="sec-2-4"></a>
### 2.4 메모리 검사
<div align="right"><a href="#toc">[목차로]</a></div>

```bash
valgrind --leak-check=full --show-leak-kinds=all ./push_swap 3 1 2 > /dev/null
```

정상 실행과 모든 에러 경로에서 누수 없이 종료됩니다.
